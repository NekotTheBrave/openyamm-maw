# MM9 Destructible Geometry Goal

## Status

Planning and source audit. The Thronheim City prison breakout is the first required vertical slice. The current MM9
import preserves the source object and script evidence in generated audit sidecars, but it does not promote
`DestructableBrush` objects into runtime scene data. Destructible BModels therefore remain permanently rendered,
collidable, pickable, and navigation-blocking.

This goal is not complete when the wall merely becomes invisible. Destruction must consistently affect rendering,
party and actor collision, floor support, projectiles, picking, line of sight, navigation, map persistence, and the
scripted encounter that caused the transition.

The source inventory used for this audit found:

- 261 `DestructableBrush` objects across 23 imported MM9 maps;
- 174 `DestructableProp` objects across 10 imported MM9 maps;
- all 261 destructible brushes authored with `ShouldMiniSave = 1`;
- 223 brushes initially authored with `CanDamage = 1` and 38 with `CanDamage = 0`;
- 22 brushes authored with `TriggerDestroyOnly = 1`; and
- at least 32 SCR files that explicitly send a `destroy` message.

These counts are an audit baseline, not hardcoded acceptance data. The checked-in generated audit must become the
authoritative inventory after destructible classification, exact geometry binding, trigger reachability, and
destructible-prop representation are implemented.

The current human-readable brush index is `MM9_DESTRUCTIBLE_BRUSH_INVENTORY.md`. It lists every checked map,
source/OpenYAMM positions, source identity/material clues, and authored destruction behavior, and is regenerated by
`tools/mm9_import_discovery/generate_mm9_destructible_brush_inventory.py`.

## Objective

Import MM9 destructible geometry as typed, persistent map-object state backed by the existing OpenYAMM world geometry
systems.

The completed implementation must:

- derive destructibility and initial state from original MM9 DAT object properties;
- bind destructible brushes to their exact converted BModel geometry by stable source identity;
- preserve the distinction between ordinary damage, trigger-only destruction, and unconditional scripted removal;
- allow imported or explicitly authored map behavior to destroy an object through a small shared event API;
- remove destroyed geometry from every world consumer in the same logical transition;
- preserve destroyed and partially damaged state across save/load and ordinary map re-entry;
- restore initial state only through the map's authoritative respawn/reset policy;
- reproduce the Thronheim City prison breakout without adding a general MM9 SCR runtime; and
- add no meaningful runtime cost when MM9 is not mounted or when a loaded map has no destructible geometry.

Use the original MM9 misspelling, `DestructableBrush`, only when retaining source class/property provenance. New
OpenYAMM types and APIs should use the correctly spelled `Destructible`.

## Source Authority

Use local sources in this order:

1. The original extracted MM9 DAT object and world model, including class, name, properties, flags, and geometry.
2. The assigned SCR and only the routines and includes reachable from the relevant object or encounter triggers.
3. DAT trigger volumes, target/message outputs, named markers, spawners, and other encounter linkages.
4. The local LithTech-family source as a structural cross-check for inherited property semantics, not as proof of the
   exact MM9 game DLL implementation and not as code to copy.
5. Existing shared OpenYAMM BModel-world rendering, collision, navigation, event, actor, and save systems as the target
   runtime contract.

Generated `*.raw_objects.yml`, `*.events.yml`, and `*.mm9.yml` files are reproducible evidence from the original DAT.
They are not authoritative hand-edit points. Fix the importer or add an explicit reviewed authored overlay instead of
editing generated output.

## Recovered Source Model

MM9 uses a hybrid object-and-script model rather than encoding the entire behavior in geometry or in SCR alone.

The DAT owns:

- the `DestructableBrush` or `DestructableProp` object class;
- the stable object name and position;
- visible, solid, ray-hit, gravity, box-physics, and fire-through state;
- `HitPoints`, `CanDamage`, `Destructable`, and `TriggerDestroyOnly`;
- damage and death trigger target/message fields;
- optional spawned-object behavior;
- debris material, amount, scale, sound, lifetime, damage, and radius properties;
- `ShouldMiniSave`; and
- a matching movable world model for destructible brushes.

SCR may own:

- when damage is enabled or disabled through messages such as `DamageOn`;
- ordinary damage callbacks;
- an unconditional `Destroy` message;
- removal without destruction effects through `RemoveObject`;
- encounter choreography leading to destruction;
- death-trigger consequences; and
- source-specific persistence or reset behavior in addition to the object save flag.

The important source semantics are therefore:

| Operation | Intended meaning |
| --- | --- |
| Ordinary damage | Reduce HP only when damage is enabled and the object is not trigger-destroy-only. |
| `DamageOn` / `DamageOff` | Change whether the object accepts ordinary damage. |
| `Destroy` | Unconditionally enter the destroyed state, bypassing remaining HP. |
| `RemoveObject` | Remove the object without inventing damage, debris, or death-trigger behavior. |
| Map respawn/reset | Reconstruct the source-authored initial state through the normal map reset policy. |

Do not collapse these operations into a single visibility flag.

## Motivating Case: Thronheim City Prison Breakout

The original `THRONHEIMCITY.dat` contains source object 65:

```text
class: DestructableBrush
name: PrisonWall
Visible: 1
Solid: 1
RayHit: 1
CanDamage: 1
Destructable: 1
TriggerDestroyOnly: 0
HitPoints: 2000
BoxPhysics: 1
ShouldMiniSave: 1
debris material: Stone
```

The converted world contains a movable world model also named `PrisonWall`, currently BModel index 39. The event audit
already resolves source object 65 to this geometry by exact source-model and BModel name. Runtime code must use a
stable map-object identity, not hardcode BModel index 39, because regeneration may change converted indexes.

DAT trigger volumes 78 and 79, named `BadAssTrigger` and `BadAssTrigger0`, both send `Breakout` to the actor named
`BadAss`. The actor is source object 66, a `DesertTerror` assigned `ThronHeimCity_BadAss.scr`.

The recovered encounter sequence is:

1. A party touch activates either source trigger volume.
2. The volume sends `Breakout` to `BadAss`.
3. The actor removes the one-shot `BreakOut` handler, stops, and walks to `BadAssWander1`.
4. At the marker, the actor faces the wall and begins its attack.
5. The source attaches `DestroyWall` to the `Rattack` animation key.
6. `DestroyWall` resolves the named `PrisonWall` object and sends it `Destroy`.
7. The wall disappears, nearby NPCs receive `HereComesBadAss`, and the Desert Terror continues its rampage.

The local script includes a TELP Patch 1.3 note stating that its edited behavior prevents the encounter from stalling
at the broken wall. OpenYAMM must implement the state transition deterministically and must not leave actor progression
dependent on geometry that was visually hidden but remains collidable.

The Thronheim slice is a required acceptance case because the wall controls progression and can strand the party or
encounter actors if destruction is incomplete.

## Current OpenYAMM Gap

Two importer paths currently disagree:

- `generate_mm9_events.py` recognizes `DestructableBrush` as `destructible_brush`, inventories its SCR references, and
  can report an exact BModel binding.
- `transcode_mm9_dat_to_odm.py` does not include `DestructableBrush` in the scene mechanism classes, so no runtime
  definition is emitted into `<map>.scene.yml`.

The generated event inventory also drops destructible gameplay properties from its normalized property subset. The raw
sidecar retains them, but HP, damage eligibility, trigger-only state, and persistence are not available to runtime
loaders.

The current outdoor mechanism runtime accepts only linear or rotational endpoint motion. A no-motion destructible
would be skipped even if it were added to the existing mechanism list. The render and navigation cookers similarly
classify only moving mechanisms as dynamic, leaving destructible BModels inside static render chunks and static cooked
navigation.

The Thronheim trigger volumes and actor SCR are discovery data only. Generated map Lua does not execute the volume
outputs or the actor's general combat/navigation script. This is consistent with the deliberate boundary against a
general MM9 SCR VM, but it means an explicit compiled profile or authored encounter overlay is required.

## Non-Negotiable Architecture

- Reuse the shared BModel-world renderer, collision cache, picking, LOS, projectile, floor-support, navigation, event,
  actor, map-delta, and save systems.
- Do not add an MM9-only geometry renderer, collision collection, path map, damage system, or save store.
- Reuse the existing dynamic-BModel resource path, but do not encode destroyed geometry as an open door.
- Represent door motion and destructible lifetime as distinct typed states.
- Bind runtime state by stable map id plus source object/runtime object id. A generated BModel index is only a resolved
  definition detail.
- Make the state transition authoritative once. Rendering and collision must not maintain independent destroyed flags.
- Do not directly edit generated MM9 scene, event, raw-object, navigation, or render sidecars.
- Do not introduce a general MM9 SCR interpreter or compile generic MM9 actor AI.
- Use a strict build-time conversion for supported source behavior and an explicit reviewed map overlay when an
  encounter cannot be represented by a generic declarative profile.
- Fail generation or the relevant completion gate for required progression behavior that would otherwise become a
  no-op.
- Preserve MM6/MM7/MM8 and `classic_odm` behavior. Destructible BModel resources must be opt-in scene data.

## Generated Data Contract

Add one authoritative generated representation for destructible geometry. A suitable scene shape is:

```yaml
destructibles:
  - object_id: 900065
    source_object_index: 65
    source_class: "DestructableBrush"
    source_name: "PrisonWall"
    binding:
      target_kind: "odm_bmodel"
      bmodel_index: 39
      bmodel_name: "PrisonWall"
      confidence: "exact_source_model_name"
    initial_state:
      visible: true
      solid: true
      can_damage: true
      trigger_destroy_only: false
      hit_points: 2000
      destructible: true
      should_mini_save: true
    debris:
      material: "stone"
      amount: 10
      scale: 1.0
      lifetime_seconds: 10.0
    outputs:
      on_damage: []
      on_destroy: []
```

The exact schema may follow established scene conventions, but it must retain:

- source object and BModel provenance;
- a stable runtime object id;
- exact binding confidence and an explicit unresolved state;
- initial visibility and collision state;
- initial and maximum HP;
- initial damage-enabled and trigger-only state;
- destruction/removal eligibility;
- persistence/reset policy;
- damage and death trigger outputs;
- spawned-object metadata; and
- typed debris/effect metadata.

Do not duplicate mutable destructible state in scene YAML, generated Lua, and an MM9-specific C++ table. Scene data
defines the object; one shared runtime state owns its current values.

`DestructableProp` requires an equivalent stable object-state contract, but its resolved render representation may be
a baked model instance, sprite/model entity, or BModel. Do not force props through a BModel-only representation when
the converted asset is not a BModel.

## Import And Property Decoding

Extend the DAT importer to classify destructible objects before static render/navigation cooking.

For each `DestructableBrush`:

1. Preserve all gameplay-relevant properties with their original names and typed normalized values.
2. Resolve the matching world model by exact normalized source name whenever possible.
3. Reject ambiguous bindings for progression-critical objects.
4. Emit the typed runtime definition into the generated scene.
5. Mark the bound geometry dynamic for render and navigation cooking.
6. Retain source path, object index, property provenance, and script/trigger references in reports.

Fix the known MM9 property-type mismatch before using debris values. In the Thronheim source, property code 6 stores
`Amount` and `Volume` as authored float bytes (`10.0` and `100.0`), but the current decoder exposes their bit patterns
as large integers. Add source-backed decoding tests across all affected properties rather than special-casing the
Thronheim object.

The importer must emit a deterministic audit covering every destructible object, its binding, runtime representation,
damage mode, persistence policy, reachable script operations, and any unresolved dependency.

## Runtime State And APIs

Add a shared state equivalent to:

```cpp
struct RuntimeDestructibleState
{
    int currentHitPoints = 0;
    bool damageEnabled = false;
    bool destroyed = false;
    bool removed = false;
};
```

Destroyed and removed may be one mutually exclusive enum if that makes invalid combinations impossible. The runtime
must still preserve the semantic distinction for effects and trigger outputs.

Expose a small shared event surface equivalent to:

```text
DamageMapObject(runtimeObjectId, amount, damageType, source)
SetMapObjectDamageEnabled(runtimeObjectId, enabled)
DestroyMapObject(runtimeObjectId)
RemoveMapObject(runtimeObjectId)
```

Generated or authored Lua resolves MM9 names and handles to stable runtime object ids at build/import time. Runtime Lua
must not search geometry by English display name or hardcoded BModel index.

Required semantics:

- ordinary damage does nothing when damage is disabled;
- ordinary damage does not destroy a `TriggerDestroyOnly` object;
- HP cannot underflow or execute destruction twice;
- `DestroyMapObject` bypasses HP and is idempotent;
- `RemoveMapObject` is idempotent and does not invent debris or death outputs;
- damage outputs execute in source order for accepted damage;
- destruction outputs and spawned-object behavior execute exactly once; and
- unsupported required output operations are visible generation/runtime failures, not silent no-ops.

## Geometry State Transition

When a BModel destructible becomes destroyed or removed, update every geometry consumer from the same authoritative
state transition.

### Rendering

- Exclude destructible BModels from static BModel-world chunks at cook time.
- Keep their faces in the existing dynamic BModel batch path while intact.
- Submit no intact-geometry faces after destruction/removal.
- Invalidate the outdoor surface visual revision so resolved draw resources refresh promptly.
- Remove or invalidate attached marks, decals, and cached lighting data that cannot outlive the geometry.

### Collision, Picking, LOS, And Projectiles

- Remove every face of the destroyed BModel from the authoritative outdoor face geometry cache.
- Rebuild or incrementally update occupied spatial cells without leaving stale blockers.
- Update the party and actor movement controllers with the same resulting face set.
- Ensure picking, LOS, ray tests, and projectile collision no longer hit removed faces.
- If a destroyed floor supported the party or an actor, invalidate support immediately and enter the normal falling
  path on the next movement update.

Destruction is infrequent. Prefer a simple correct full face-cache/spatial-index rebuild on destruction before adding
targeted removal complexity. Door animation remains on its existing incremental hot path.

### Navigation

- Mark destructible faces as dynamic in cooked navigation metadata.
- Remove destroyed geometry references from the live navigation facet set.
- Invalidate and rebuild the affected path map after a destruction/removal endpoint transition.
- Preserve intact destructible floors and barriers before destruction.
- Do not rebuild navigation continuously while the object is merely taking damage.

The existing cooked-navigation builder already skips source references whose live geometry is absent. Use that shared
identity rather than maintaining a separate MM9 blocker list.

## Damage Integration

Implement scripted destruction first because it is required for progression, then complete source-authorized ordinary
damage.

Party projectiles already resolve BModel impact geometry. Route an impact into the shared map-object damage operation
when its BModel belongs to an intact damageable object. Preserve the resolved attack damage and damage type; do not
invent a second MM9 damage formula.

Melee attacks must similarly be able to hit an eligible destructible object through the shared attack/interaction ray.
Area attacks should damage nearby eligible objects only when the existing shared attack semantics say world objects
receive that effect. Do not make every cosmetic particle or collision event deal damage.

Source debris, sounds, explosion damage, radius, and spawned-object effects may be implemented incrementally after the
geometry transition is correct. Their metadata and unsupported status must remain explicit in the meantime.

## Thronheim Encounter Integration

The Thronheim encounter belongs jointly to this goal and `MM9_SCRIPTED_ACTOR_IMPORT_GOAL.md`:

- this goal owns the typed `PrisonWall` object and its destruction transition;
- the scripted-actor goal owns the source-driven classification and shared actor behavior for `BadAss`, nearby NPCs,
  and guards; and
- an explicit `thronheimcity_authored.lua` or declarative encounter profile may connect the source trigger volumes,
  marker movement, attack action, object destruction, and follow-up actor messages.

Do not compile `BASEMELEE.inc`, wandering, obstacle handling, socializing, or the complete source actor state machine.
Map the source intent onto shared OpenYAMM behavior:

- one-shot party touch volume;
- actor message/encounter activation;
- walk or run to a named imported marker;
- face a target point;
- play the shared attack action;
- destroy the stable map object at the attack action point; and
- continue through shared hostile actor behavior and explicit encounter actions.

If imported model-key callbacks are not part of the shared actor animation representation, the authored encounter
must define destruction as part of the attack action transition. It must not wait indefinitely for an unavailable MM9
animation key or use a polling/watchdog workaround.

Both source trigger volumes must activate the same idempotent encounter state. Save/load before activation, while the
actor approaches the wall, and after destruction must not duplicate the encounter or restore the wall incorrectly.

## Persistence And Respawn

Persist current HP, damage-enabled state, and destroyed/removed state in the existing per-map outdoor snapshot. Scene
definitions and BModel bindings are map-derived and must be rebuilt from current content after save load so regenerated
geometry does not inherit stale saved BModel indexes.

Required lifecycle behavior:

- ordinary save/load preserves partial damage and destruction;
- ordinary map exit and re-entry preserves the map object's state;
- a mini-save-equivalent path preserves objects authored with `ShouldMiniSave`;
- map respawn/reset reconstructs the initial DAT state according to the existing authoritative respawn policy;
- old saves without destructible state initialize from current scene data; and
- save migration is explicit and versioned rather than inferred from missing geometry.

Do not use party QBits as a hidden substitute for map-object persistence unless the original encounter explicitly owns
such a QBit.

## Implementation Phases

### Phase 0: Exhaustive Audit

Generate a deterministic inventory for every MM9 destructible brush and prop. Record properties, exact geometry/entity
binding, damage mode, persistence, assigned script, reachable `Destroy`, `DamageOn`, `DamageOff`, and `RemoveObject`
operations, trigger/death outputs, and unresolved behavior.

Classify every object as:

- bound destructible BModel;
- bound destructible prop/entity;
- scripted removal-only object;
- non-destructible despite its archetype;
- ambiguous binding; or
- unsupported required behavior.

### Phase 1: Typed BModel Destruction

Implement scene schema, loader, dynamic cooking, runtime state, save serialization, and the unconditional shared
destroy/remove operations. Add focused synthetic and real-map headless coverage proving one BModel disappears from all
geometry consumers and remains absent after save/load.

### Phase 2: Thronheim Vertical Slice

Regenerate Thronheim City with source object 65 as a typed destructible. Add the reviewed encounter linkage for source
trigger volumes 78/79 and actor 66. Verify that the prison-to-marketplace passage becomes traversable and remains so
after save/load.

### Phase 3: Ordinary Damage

Route shared projectile, melee, and applicable area damage into destructible state. Implement `CanDamage`,
`TriggerDestroyOnly`, HP, `DamageOn`, and `DamageOff`. Validate representative stone, wood, glass, trigger-only, and
initially damage-disabled objects.

### Phase 4: Effects, Outputs, And Props

Implement source-authorized debris, sound, explosion, spawn, damage-trigger, and death-trigger behavior. Promote
`DestructableProp` objects through their actual converted render representation without duplicating BModel state.

### Phase 5: Full Regeneration And Closure

Regenerate all MM9 maps, cooked render/navigation sidecars, event data, Lua, and audits. Resolve every progression-
critical unsupported object and document non-critical explicitly deferred effects. Perform focused MM6/MM7/MM8
regression coverage alongside the MM9 gates.

## Automated Completion Gates

### Importer And Schema

- Synthetic DAT fixtures prove all gameplay-relevant destructible properties retain correct types.
- Real Thronheim source object 65 binds exactly to `PrisonWall` without a contradictory unresolved diagnostic.
- Ambiguous progression-critical bindings fail generation.
- Destructible definitions round-trip through scene loading and authored overlays.
- Render and navigation cookers classify bound destructible BModels as dynamic.
- Regeneration leaves authored scene and Lua overlays untouched.
- The generated audit accounts for every `DestructableBrush` and `DestructableProp` object.

### Shared Runtime

- An intact destructible is visible, collidable, pickable, projectile-blocking, LOS-blocking where appropriate, and
  present in navigation.
- `DestroyMapObject` removes it from all those consumers in one update and is idempotent.
- `RemoveMapObject` suppresses destruction effects while removing the same geometry state.
- Destroying a supporting floor makes supported entities enter normal falling behavior.
- Partial HP, damage-enabled state, and destruction survive save/load and map re-entry.
- Map respawn restores initial state exactly once according to map policy.
- Trigger-only objects ignore ordinary damage and accept explicit destruction.
- Initially damage-disabled objects become damageable only after the source-authorized state transition.

### Thronheim City

- Either imported source trigger volume 78 or 79 activates the breakout once.
- `BadAss` reaches the wall action point and destroys source object 65.
- The intact wall blocks the prison passage before activation.
- The destroyed wall does not render or collide and the prison-to-marketplace route becomes traversable.
- Actor pathfinding can continue through the former wall location.
- Saving before activation, during approach, and after destruction restores a coherent encounter state.
- Reloading after destruction cannot resurrect the wall or strand the party.

### Compatibility And Performance

- Representative MM6/MM7/MM8 classic ODM rendering, collision, projectiles, picking, LOS, navigation, and mechanisms
  retain existing behavior.
- Existing moving BModel doors and lifts retain render/collision/navigation/save parity.
- Maps with no destructible definitions allocate no destructible runtime collections beyond empty defaults and add no
  checks to classic hot loops.
- MM9 not mounted adds no meaningful startup, map-load, memory, or per-frame cost.
- No temporary diagnostic logging, polling timers, map-name conditionals, or hardcoded Thronheim BModel indexes remain.

## Manual Completion Gates

In a desktop Thronheim City playthrough:

1. Confirm the prison wall is visibly and physically intact before the encounter.
2. Activate the encounter through each reachable source trigger approach.
3. Confirm the Desert Terror approaches, attacks, and opens the passage without stalling.
4. Walk the party through the destroyed opening into the encounter route.
5. Confirm nearby actors and guards continue their intended encounter behavior.
6. Save and reload immediately before destruction, during the approach, and after entering the marketplace.
7. Confirm no invisible collision, floating marks, stale projectile impacts, actor navigation stalls, or wall
   resurrection occurs.

Review representative non-Thronheim destructibles, including ordinary damage, trigger-only, damage-disabled, falling
floor, and mass scripted-destruction cases. Confirm that deferred debris/effect differences are documented and do not
hide progression blockers.

## Definition Of Done

This goal is complete only when:

- every MM9 destructible brush and prop has a deterministic generated classification;
- every progression-critical destructible has an exact runtime binding and executable destruction path;
- destruction updates rendering, collision, support, picking, LOS, projectiles, and navigation consistently;
- ordinary damage and trigger-only semantics match the recovered source model;
- map-object state survives save/load and ordinary map re-entry without stale geometry indexes;
- the complete Thronheim prison breakout and passage work through shared OpenYAMM systems;
- unsupported non-critical effects are explicitly inventoried rather than silently ignored;
- focused automated and manual gates pass; and
- affected MM6/MM7/MM8 paths show no behavioral or performance regression.
